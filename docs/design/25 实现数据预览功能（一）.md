## 一、概述

前面二十几篇把"接待"这件事做完了：渠道能接入、机器人能答、坐席能接、工单能跟、质检能查、客户有画像。

但**管理者打开系统第一眼看什么？**

总得有个地方把今天的情况一屏说清楚：今天接待了多少人、机器人顶住了多少、客户满意不满意、坐席忙不忙、有没有会话在排队、有没有工单要超时。

这一篇做**数据预览页**（菜单里的「数据概览」）：把散在各处的业务数字汇总成一屏，并且**只展示系统自己算得准的数据**——不用人工维护、也不引外部报表系统。

### 1.1 功能定位

|              |                                                                                                           |                                            |
|--------------|-----------------------------------------------------------------------------------------------------------|--------------------------------------------|
| 功能模块     | 说明                                                                                                      | 使用场景                                   |
| 今日概览     | 页头问候 + 日期 + "当前 N 个会话等待接待 · M 个工单临近 SLA"                                              | 管理者每天打开系统第一眼                   |
| 6 张 KPI     | 今日会话、机器人接待率、平均首响时长、客户满意度、在线坐席、排队会话，每张带"较昨日"涨跌与近 8 天迷你折线 | 一眼看出"今天比昨天好还是差"               |
| 会话趋势     | 近 14 天会话总量 + 机器人接待量（双线）                                                                   | 看量级走势与机器人承担比例                 |
| 渠道分布     | 今日各渠道会话占比（环形图 + 图例百分比）                                                                 | 判断流量从哪来                             |
| 满意度趋势   | 近 7 日好评率（4\~5 星占比）+ 右上角整体好评率                                                            | 质量有没有滑坡                             |
| 坐席实时状态 | 今日服务量 Top 6 + 在线/忙碌/离线状态点 + 在接会话数                                                      | 决定要不要把排队的会话手动分给人           |
| 实时动态     | 今日事件流：发起会话 / 转人工 / 客户评价 / 新建工单 / 实时质检预警                                        | 值班时盯着这一块就能知道刚发生了什么       |
| 待办工单     | 在办工单按 SLA 排（超时 &gt; 临近 &gt; 正常），点行直接打开工单详情                                       | 先处理最可能超时的                         |
| 待办中心     | 聚合四类待办：SLA 预警工单、质检待复核、实时质检告警、排队会话，点一条直达对应页面                        | 一个入口把所有"该我干的事"看全             |
| TOP 高频问题 | 今日意图分布 Top 5（带占比条）                                                                            | 判断知识库该补哪块                         |
| 权限与容错   | 经营数据只有管理员 / 主管能看；接口失败页面给明确告警而不是空白                                           | 一线客服不该看经营数字，后端不该"静默空着" |

### 1.2 数据链路

先看清楚"页面上的每个数字是谁算出来的"——这一篇没有任何人工录入的数据：

``` code-block-container
  业务事实（本系统自己产生的数据）                    实时指标接口                    数据预览页
  ────────────────────────────────────           ──────────────────         ──────────────────
  session（排队/机器人/人工/已结束）        ┐
  session_message（谁在什么时候说了什么）    │
  csat_record（客户打分 1~5）               ├──►  selectRealtimeOverview   ──►  6 张 KPI：会话 / 机器人
  agent_status（在线 / 忙碌 / 小休）         │     selectTodayMetrics            接待率 / 首响 / 满意度
  session_event（转人工）                   │     selectHourlyTrend              / 在线坐席 / 排队
  ticket（工单 SLA）                       │     selectChannelDistribution
  qa_alert（实时质检告警）                  │     selectIntentDistribution  ──►  渠道分布 / TOP 高频问题
  customer / channel（客户与渠道名）         │     selectEmotionDistribution
                                          │     selectAgentLive           ──►  坐席实时状态
  agent_daily_metric（坐席 × 天预聚合）      ┘     selectRecentActivity      ──►  实时动态
        └── selectTenantTrend ──► 会话趋势 / 满意度趋势（近 14 天）

  页面之外还有两块"待办"取自既有接口：待办工单 → /customer/tickets，待办中心 → /customer/qa/overview
```

两个关键设计：

1.  **今天的数据现算、历史趋势读预聚合**：今天的会话量、排队数、在线坐席都是"此刻"的口径，直接查 `session` / `agent_status`（只看今天，数据量小）；近 14 天趋势需要按天汇总，读 `agent_daily_metric`（坐席 × 天预聚合），不然每次刷新都要全表扫 `session_message`；

2.  **一个接口组装一屏**：页面只调 `/customer/metrics/realtime` 一次，服务端把十几条查询组装成一个对象返回，避免首屏十几个请求互相抢带宽。

### 1.3 指标口径

口径是这一篇最需要写清楚的部分——同一个词用不同算法，页面上两个数字就会互相矛盾。

|              |                                                                                          |                            |
|--------------|------------------------------------------------------------------------------------------|----------------------------|
| 指标         | 口径                                                                                     | 数据来源                   |
| 今日会话     | `start_time` 落在今天 00:00 \~ 此刻的会话条数                                            | `session`                  |
| 机器人接待率 | 机器人独立接待（`status=2` 或 `bot_transfer_reason` 非空）÷ 今日会话                     | `session`                  |
| 平均首响时长 | 客户最后一条 → 坐席第一条（只算对客户可见的回复）的秒级平均                              | `session_message`          |
| 客户满意度   | **好评率** = 4~~5 星评价数 ÷ 当日评价总数（不是 1~~5 的均分）                            | `csat_record`              |
| 在线坐席     | 长连接在线且 `status=1`（空闲）的人数；分母是租户下已登记过状态的坐席总数                | `agent_status`             |
| 排队会话     | `status=1`（排队中）的会话数；"进行中"= `status IN (2,3)`（机器人 / 人工接待中）         | `session`                  |
| 渠道分布     | 今日会话按渠道名聚合（取不到渠道名时退化为 `source`）                                    | `session` + `channel`      |
| TOP 高频问题 | 今日会话按 `intent` 聚合 Top 5（意图由 AI 客服大脑写入）                                 | `session`                  |
| 坐席实时状态 | 状态来自 `agent_status`；服务量 / 满意度来自今天的会话                                   | `agent_status` + `session` |
| 实时动态     | 今天的会话发起 / 转人工（`event_type=6`）/ 评价 / 新建工单 / 质检预警，按时间倒序取 8 条 | 五张业务表 UNION           |
| 近 14 天趋势 | 按天汇总的会话数 / 机器人接待数 / 消息数 / 好评数                                        | `agent_daily_metric`       |

> **"满意度"为什么用好评率**：1\~5 分制里 4.2 分和 4.6 分对运营没有体感，而"100 个客户里 93 个给了 4 星以上"一眼就懂；坐席绩效报表里用的也是同一个口径（`good_csat_count`），两处必须一致，否则同一件事两个页面两个数。

## 二、数据库设计

### 2.1 增量脚本（整份）

这一篇只新增一张表：`agent_daily_metric`（坐席 × 天的预聚合）。为什么要有它、以及"为什么不每次现算"，脚本头部注释里写得很清楚：

-   数据预览页 15 秒刷一次，近 14 天趋势如果每次都去 `session_message` 上现算，等于每 15 秒全表扫一遍；

-   预聚合之后，趋势只读几十行（5 个坐席 × 14 天）；

-   重算是**幂等**的：同一个坐席同一天算多少次结果都一样（`ON CONFLICT … DO UPDATE`）。

### 文件：schema/customer\_db\_metrics.sql

客户库增量脚本：坐席 × 天预聚合表 + 索引 + 注释。表里的 `agent_id = 0` 表示"未分配 / 机器人接待"那一行——Postgres 里 NULL 不参与唯一约束，所以不能用 NULL 当"未分配"的键。

``` code-block-container
-- 云梯智能客服平台 · customer_db 数据大屏与坐席绩效增量脚本（PostgreSQL 17）
-- 用途：把"报表要用的数字"按 坐席 × 天 预聚合出来，供大屏与绩效报表快速读取。
--   新增 agent_daily_metric：一天的接待量 / 消息量 / 首响时长 / 会话时长 / 满意度 / 转接次数…
-- 幂等：可重复执行（CREATE TABLE IF NOT EXISTS + 索引 IF NOT EXISTS）。
--
-- 为什么要预聚合而不是每次现算：
--   1. 绩效报表要按坐席筛选、排序、分页、再下钻，现算就得对 session_message 做全表聚合，
--      数据量一大就拖死列表；
--   2. 大屏要 5 秒刷新一次，每次都全表扫是浪费——预聚合之后大屏只读今天的几十行。
--   重算是**幂等**的：同一个坐席同一天重算多少次结果都一样（DELETE + INSERT 或 UPSERT）。

CREATE TABLE IF NOT EXISTS "agent_daily_metric" (
  "id" BIGINT NOT NULL,
  "tenant_code" VARCHAR(16) NOT NULL,
  "agent_id" BIGINT DEFAULT NULL,
  "agent_name" VARCHAR(64) DEFAULT NULL,
  "stat_date" DATE NOT NULL,
  "session_count" INT NOT NULL DEFAULT 0,
  "human_session_count" INT NOT NULL DEFAULT 0,
  "message_count" INT NOT NULL DEFAULT 0,
  "customer_message_count" INT NOT NULL DEFAULT 0,
  "first_response_seconds" INT NOT NULL DEFAULT 0,
  "avg_response_seconds" INT NOT NULL DEFAULT 0,
  "avg_session_seconds" INT NOT NULL DEFAULT 0,
  "transfer_count" INT NOT NULL DEFAULT 0,
  "csat_count" INT NOT NULL DEFAULT 0,
  "csat_score" NUMERIC(5,2) DEFAULT NULL,
  "good_csat_count" INT NOT NULL DEFAULT 0,
  "close_count" INT NOT NULL DEFAULT 0,
  "create_time" TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  "update_time" TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY ("id"),
  CONSTRAINT "uk_tenant_agent_date" UNIQUE ("tenant_code", "agent_id", "stat_date")
);

-- 报表默认按"最近 30 天 + 租户"筛，再按坐席聚合；这条索引撑住它
CREATE INDEX IF NOT EXISTS "idx_agent_metric_tenant_date"
    ON "agent_daily_metric" ("tenant_code", "stat_date" DESC);

COMMENT ON TABLE "agent_daily_metric" IS '坐席绩效日聚合表（按 坐席 × 天 预聚合，报表与大屏都读它）';
COMMENT ON COLUMN "agent_daily_metric"."agent_id" IS '坐席用户ID（0 表示"未分配/机器人接待"这一行）';
COMMENT ON COLUMN "agent_daily_metric"."stat_date" IS '统计日期（按自然日）';
COMMENT ON COLUMN "agent_daily_metric"."session_count" IS '接待会话数（含机器人阶段后转过来的）';
COMMENT ON COLUMN "agent_daily_metric"."human_session_count" IS '人工接待过的会话数';
COMMENT ON COLUMN "agent_daily_metric"."message_count" IS '这条坐席发的消息数（不含内部备注？含，备注也是坐席产出）';
COMMENT ON COLUMN "agent_daily_metric"."customer_message_count" IS '客户发的消息数（用来算"人均沟通量"）';
COMMENT ON COLUMN "agent_daily_metric"."first_response_seconds" IS '首次响应时长均值（秒）：客户最后一条 → 坐席第一条，按会话平均';
COMMENT ON COLUMN "agent_daily_metric"."avg_response_seconds" IS '平均响应时长（秒）：坐席每次回复距客户上一条消息的平均间隔';
COMMENT ON COLUMN "agent_daily_metric"."avg_session_seconds" IS '平均会话时长（秒）：会话开始到结束';
COMMENT ON COLUMN "agent_daily_metric"."transfer_count" IS '转接次数（session_event 的转接事件）';
COMMENT ON COLUMN "agent_daily_metric"."csat_count" IS '收到的评价条数';
COMMENT ON COLUMN "agent_daily_metric"."csat_score" IS '满意度均值（1~5）';
COMMENT ON COLUMN "agent_daily_metric"."good_csat_count" IS '好评数（4~5 分）';
COMMENT ON COLUMN "agent_daily_metric"."close_count" IS '结束的会话数（状态 4）';
```

### 2.3 索引与约束

\| 名称 \| 类型 \| 字段 \| 作用 \|  
\| --- \| --- \| --- \|  
\| `uk_tenant_agent_date` \| 唯一 \| tenant\_code, agent\_id, stat\_date \| 一个坐席一天一行，重算靠它 UPSERT \|  
\| `idx_agent_metric_tenant_date` \| 普通 \| tenant\_code, stat\_date DESC \| 趋势查询按"租户 + 日期区间"取数 \|

> 踩过的两个坑都写进注释与脚本里了：**① 主键不能用"agent\_id × 1e8 + 日期"这种算术拼接**（19 位雪花乘完直接 bigint 溢出），改用 `hashtextextended` 做 64 位哈希；**②** `agent_id` **为 NULL 躲得过唯一约束**，会把"未分配"那行插成多行，所以统一落 0。

    <!--
      重算某一天的坐席绩效：一条 SQL 把四个指标来源合成一行（坐席 × 天），再 upsert。

      三处口径说明（都在报表页脚注里写清楚了）：
        · 首次响应 = 客户最后一条消息 → 坐席第一条消息（内部备注不算"响应"，客户看不到）；
        · 平均响应 = 坐席每条消息距"客户上一条消息"的间隔（LATERAL 取上一条客户消息）；
        · 会话时长 = start_time → end_time（未结束的会话按 now() 算，所以白天的数字会继续涨）。

      坐席姓名**不在 SQL 里取**：sys_user 在另一个库（user_db），跨库 join 不了——
      读取时由 UserNameClient 调 user-service 的内部接口批量换名字（见 MetricsService）。

    <insert id="rebuildDaily">
        WITH base AS (
            SELECT s.id,
                   s.tenant_code,
                   s.agent_id,
                   s.start_time,
                   s.end_time,
                   s.status,
                   s.csat_score
              FROM session s
             WHERE s.tenant_code = #{tenantCode}
               AND s.is_deleted = FALSE
               AND s.start_time &gt;= #{from}
               AND s.start_time &lt; #{to}
        ),
        msg AS (
            SELECT m.session_id,
                   COUNT(1) FILTER (WHERE m.sender_type = 2) AS agent_msgs,
                   COUNT(1) FILTER (WHERE m.sender_type = 1) AS customer_msgs
              FROM session_message m
             WHERE m.tenant_code = #{tenantCode}
               AND m.is_deleted = FALSE
               AND m.send_time &gt;= #{from}
               AND m.send_time &lt; #{to}
             GROUP BY m.session_id
        ),
        first_agent AS (
            SELECT m.session_id, MIN(m.send_time) AS first_at
              FROM session_message m
             WHERE m.tenant_code = #{tenantCode}
               AND m.is_deleted = FALSE
               AND m.sender_type = 2
               AND m.visible_to = 1
             GROUP BY m.session_id
        ),
        last_customer AS (
            SELECT m.session_id, MAX(m.send_time) AS last_at
              FROM session_message m
             WHERE m.tenant_code = #{tenantCode}
               AND m.is_deleted = FALSE
               AND m.sender_type = 1
             GROUP BY m.session_id
        ),
        -- 坐席每条消息的"响应间隔"：距它前面最近的一条客户消息
        resp AS (
            SELECT m.session_id, AVG(EXTRACT(EPOCH FROM (m.send_time - prev.customer_at))) AS avg_seconds
              FROM session_message m
              JOIN LATERAL (
                    SELECT MAX(c.send_time) AS customer_at
                      FROM session_message c
                     WHERE c.tenant_code = m.tenant_code
                       AND c.session_id = m.session_id
                       AND c.sender_type = 1
                       AND c.is_deleted = FALSE
                       AND c.send_time &lt; m.send_time
                   ) prev ON TRUE
             WHERE m.tenant_code = #{tenantCode}
               AND m.is_deleted = FALSE
               AND m.sender_type = 2
               AND prev.customer_at IS NOT NULL
             GROUP BY m.session_id
        ),
        transfer AS (
            SELECT e.session_id, COUNT(1) AS cnt
              FROM session_event e
             WHERE e.tenant_code = #{tenantCode}
               AND e.event_type = 1
             GROUP BY e.session_id

             create_time, update_time)
        SELECT

            hashtextextended(#{tenantCode} || ':' || COALESCE(b.agent_id, 0)::text || ':' || #{statDate}, 0) AS id,
            #{tenantCode},
            -- 未分配 / 机器人接待统一落 0：UNIQUE 约束对 NULL 不生效，留 NULL 会重复插行
            COALESCE(b.agent_id, 0) AS agent_id,
            NULL AS agent_name,
            #{statDate},
            COUNT(1) AS session_count,
            COUNT(1) FILTER (WHERE b.agent_id IS NOT NULL) AS human_session_count,
            COALESCE(SUM(msg.agent_msgs), 0) AS message_count,
            COALESCE(SUM(msg.customer_msgs), 0) AS customer_message_count,
            COALESCE(ROUND(AVG(EXTRACT(EPOCH FROM (fa.first_at - lc.last_at))))::INT, 0) AS first_response_seconds,
            COALESCE(ROUND(AVG(resp.avg_seconds))::INT, 0) AS avg_response_seconds,
            COALESCE(ROUND(AVG(EXTRACT(EPOCH FROM (COALESCE(b.end_time, now()) - b.start_time))))::INT, 0)
                AS avg_session_seconds,
            COALESCE(SUM(tr.cnt), 0) AS transfer_count,
            COUNT(b.csat_score) AS csat_count,
            ROUND(AVG(b.csat_score)::numeric, 2) AS csat_score,
            COUNT(b.csat_score) FILTER (WHERE b.csat_score &gt;= 4) AS good_csat_count,

          LEFT JOIN msg ON msg.session_id = b.id

          LEFT JOIN transfer tr ON tr.session_id = b.id
         GROUP BY COALESCE(b.agent_id, 0)

        ReportQuery q = normalize(query);
        Long id = agentId == null || agentId.isBlank() || "0".equals(agentId) ? null : Long.parseLong(agentId);
        List<Map<String, Object>> trend = metricMapper.selectAgentTrend(tenant, id, q.from(), q.to());
        List<Map<String, Object>> sessions = sessionMapper.selectAgentSessionsForReport(
                tenant, id, q.from().atStartOfDay(), q.to().plusDays(1).atStartOfDay(), DRILL_SESSION_LIMIT);
        Map<String, String> names = id == null ? Map.of() : userNameClient.namesOf(List.of(String.valueOf(id)));

        List<DayPointVO> points = new ArrayList<>();
        for (Map<String, Object> row : trend) {
            points.add(new DayPointVO(dayLabel(row.get("stat_date")), intValue(row.get("session_count")),
                    intValue(row.get("message_count")), decimalValue(row.get("csat_score")),
                    intValue(row.get("first_response_seconds"))));
        }
        List<DrillSessionVO> list = new ArrayList<>();
        for (Map<String, Object> row : sessions) {
            list.add(new DrillSessionVO(
                    stringValue(row.get("session_no")),
                    stringValue(row.get("customer_name")),
                    stringValue(row.get("source")),
                    intValue(row.get("status")),

                    timeValue(row.get("start_time")),
                    timeValue(row.get("end_time")),
                    durationMinutes(row.get("start_time"), row.get("end_time"))));
        }
        return new AgentDrillVO(id == null ? null : String.valueOf(id),
                displayName(names, id), q.from().toString(), q.to().toString(), points, list);
    }

        AgentReportVO report = agentReport(user, q, 1, EXPORT_LIMIT);
        StringBuilder csv = new StringBuilder("\ufeff");
        csv.append("坐席,活跃天数,接待会话,人工接待,坐席消息,客户消息,首次响应(秒),平均响应(秒),")
                .append("平均会话时长(秒),转接次数,评价数,满意度,好评数,结束会话,日均接待\n");
        for (AgentReportRowVO row : report.list()) {
            csv.append(csv(row.agentName())).append(',')
                    .append(row.activeDays()).append(',')
                    .append(row.sessionCount()).append(',')
                    .append(row.humanSessionCount()).append(',')
                    .append(row.messageCount()).append(',')
                    .append(row.customerMessageCount()).append(',')
                    .append(row.firstResponseSeconds()).append(',')
                    .append(row.avgResponseSeconds()).append(',')
                    .append(row.avgSessionSeconds()).append(',')
                    .append(row.transferCount()).append(',')
                    .append(row.csatCount()).append(',')
                    .append(row.csatScore() == null ? "" : row.csatScore()).append(',')
                    .append(row.goodCsatCount()).append(',')
                    .append(row.closeCount()).append(',')
                    .append(row.sessionPerDay()).append('\n');
        }
        return csv.toString();
    }

    private static String csv(String value) {
        if (value == null || value.isEmpty()) {
            return "";
        }
        String text = value.replace("\"", "\"\"");
        return text.contains(",") || text.contains("\"") || text.contains("\n")
                ? "\"" + text + "\"" : text;
    }

    /** 重算某一天的坐席绩效（幂等）。页面上的「重算」按钮与定时任务都走它。 */
    @Transactional
    public int rebuild(LoginUser user, String day) {
        String tenant = tenantOf(user);
        requireReport(user, tenant);
        LocalDate date = day == null || day.isBlank() ? LocalDate.now() : LocalDate.parse(day);
        int rows = rebuildDay(tenant, date);
        log.info("坐席绩效重算 tenant={} date={} 行数={} operator={}", tenant, date, rows, user.name());
        return rows;
    }

    private int rebuildDay(String tenant, LocalDate date) {
        return metricMapper.rebuildDaily(tenant, date, date.atStartOfDay(), date.plusDays(1).atStartOfDay());
    }

    /**
     * 定时重算：每 5 分钟把"今天"和"昨天"各算一遍。
     *
     * <p>今天要算是因为白天的数字一直在变；昨天要算是因为跨零点之后，
     * 昨晚未结束的会话变成了已结束，会话时长要补上。</p>
     */
    @Scheduled(initialDelay = 60_000, fixedDelay = 300_000)
    public void scheduledRebuild() {
        for (String tenant : sessionMapper.selectTenantsForMetrics()) {
            for (LocalDate date : List.of(LocalDate.now(), LocalDate.now().minusDays(1))) {
                try {
                    rebuildDay(tenant, date);
                } catch (Exception e) {
                    log.warn("坐席绩效定时重算失败 tenant={} date={} error={}", tenant, date, e.getMessage());
                }
            }
        }
    }

    /**
     * 启动时把近 14 天补齐。
     *
     * <p>为什么要补：报表读的是预聚合表，如果只靠"每 5 分钟算今天和昨天"，
     * 重启之后历史日期就是空的（新库、或者刚跑完演示数据时尤其明显）。
     * 14 天 × 每个租户一次 upsert，成本很低，换来"打开页面就有数据"。</p>
     */
    @org.springframework.context.event.EventListener(
            org.springframework.boot.context.event.ApplicationReadyEvent.class)
    public void warmUpHistory() {
        try {
            List<String> tenants = sessionMapper.selectTenantsForMetrics();
            for (String tenant : tenants) {
                for (int i = 0; i < 14; i++) {
                    rebuildDay(tenant, LocalDate.now().minusDays(i));
                }
            }
            if (!tenants.isEmpty()) {
                log.info("坐席绩效历史回填完成：{}", String.join("、", tenants));
            }
        } catch (Exception e) {
            log.warn("坐席绩效历史回填失败（不影响启动）：{}", e.getMessage());
        }
    }

    /**
     * 当前登录人能不能看数据报表（前端据此显隐菜单）。
     *
     * <p>为什么单独给一个接口：菜单要在进页面之前就知道该不该显示。
     * 「成员管理」的条件是"仅企业管理员"，而经营数据是"管理员 + 客服主管"能看——
     * 两者口径不一样，不能复用同一个开关。</p>
     */
    public AccessVO access(LoginUser user) {
        String tenant = tenantOf(user);
        List<String> roles = userRoleClient.rolesOf(user.userId(), tenant);
        if (roles == null) {
            return new AccessVO(false, null, "未知（用户服务不可用）", "暂时读不到你的角色，数据报表已临时收紧");
        }
        if (roles.isEmpty()) {
            return new AccessVO(true, "ADMIN", "企业管理员", "该租户还没有角色数据，按企业管理员兼容");
        }
        List<String> clean = roles.stream().filter(java.util.Objects::nonNull).toList();
        String primary = clean.stream().filter(REPORT_ROLES::contains).findFirst().orElse(clean.get(0));
        boolean canView = clean.stream().anyMatch(REPORT_ROLES::contains);
        return new AccessVO(canView, primary, ROLE_NAMES.getOrDefault(primary, primary),
                canView ? "可以查看实时大屏与坐席绩效" : "数据报表只有企业管理员 / 客服主管能看");
    }

    private String tenantOf(LoginUser user) {
        if (user == null || user.userType() != 2) {
            throw new BizException(40301, "仅企业成员可查看数据报表");
        }
        String tenant = user.tenantCode();
        if (tenant == null || tenant.isBlank() || "PLATFORM".equals(tenant)) {
            throw new BizException(40301, "请先完成企业开通后再查看数据报表");
        }
        return tenant;
    }

    /**
     * 报表权限：**只有企业管理员与客服主管**能看经营数据。
     *
     * <p>和客户 360 的"只读角色能看不能改"不同：经营数据是敏感信息（坐席之间的横向对比、
     * 客户量与满意度），一线客服看同事业绩只会制造内耗，所以这里直接拒绝。
     * 问不到角色时保守拒绝——宁可让管理员确认一下，也不要把数据漏出去。</p>
     */
    private void requireReport(LoginUser user, String tenant) {
        List<String> roles = userRoleClient.rolesOf(user.userId(), tenant);
        if (roles == null) {
            throw new BizException(40302, "暂时读不到你的角色，数据报表已临时收紧；请稍后重试或联系管理员");
        }
        if (roles.isEmpty()) {
            return;
        }
        List<String> clean = roles.stream().filter(java.util.Objects::nonNull).toList();
        if (clean.stream().noneMatch(REPORT_ROLES::contains)) {
            throw new BizException(40302, "数据报表只有企业管理员 / 客服主管能看（当前角色："
                    + ROLE_NAMES.getOrDefault(clean.isEmpty() ? "" : clean.get(0), "未知") + "）");
        }
    }

    private ReportQuery normalize(ReportQuery query) {
        LocalDate to = query != null && query.to() != null ? query.to() : LocalDate.now();
        LocalDate from = query != null && query.from() != null
                ? query.from() : to.minusDays(DEFAULT_RANGE_DAYS - 1L);
        if (from.isAfter(to)) {
            throw new BizException(40001, "开始日期不能晚于结束日期");
        }
        if (Duration.between(from.atStartOfDay(), to.plusDays(1).atStartOfDay()).toDays() > MAX_RANGE_DAYS) {
            throw new BizException(40001, "一次最多查询 " + MAX_RANGE_DAYS + " 天，请缩小范围");
        }
        return new ReportQuery(from, to,
                query == null ? null : query.agentId(),
                query == null ? null : query.sort());
    }

    private static int intValue(Object value) {

        }

        }

        }

            return Long.parseLong(String.valueOf(value).trim());
        } catch (NumberFormatException e) {

        }
    }

    private static BigDecimal decimalValue(Object value) {
        if (value == null) {
            return null;
        }
        if (value instanceof BigDecimal decimal) {
            return decimal;
        }
        if (value instanceof Number number) {
            return BigDecimal.valueOf(number.doubleValue()).setScale(2, RoundingMode.HALF_UP);
        }
        try {
            return new BigDecimal(String.valueOf(value).trim()).setScale(2, RoundingMode.HALF_UP);
        } catch (NumberFormatException e) {
            return null;
        }
    }

    private static LocalDate dateValue(Object value) {
        if (value == null) {
            return null;
        }
        if (value instanceof LocalDate date) {
            return date;
        }
        if (value instanceof java.sql.Date date) {
            return date.toLocalDate();
        }
        return LocalDate.parse(String.valueOf(value).substring(0, 10));
    }

    private static LocalDateTime timeValue(Object value) {
        if (value == null) {
            return null;
        }
        if (value instanceof LocalDateTime time) {
            return time;
        }
        if (value instanceof java.sql.Timestamp timestamp) {
            return timestamp.toLocalDateTime();
        }
        if (value instanceof java.util.Date date) {
            return LocalDateTime.ofInstant(date.toInstant(), java.time.ZoneId.systemDefault());
        }
        return null;
    }

| `agentLive[]`                                 | 坐席实时状态                             | 状态文案 / 是否在线 / 在接数 / 今日服务量 / 满意度  |

两处容错设计：

1.  **实时动态查失败只降级为空列表**：`selectRecentActivity` 会碰 `qa_alert` / `ticket` 等表，某个租户的库结构没升级时不该让整屏打不开——首页的"锦上添花"不该拖垮主指标；

2.  **问不到角色就保守拒绝**：经营数据只给管理员与客服主管，角色反查失败时按"没有权限"处理（宁可少给，不可多给）。
